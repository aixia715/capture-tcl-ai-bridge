# 安全模型

## 一句话结论

这个桥**不是沙箱**。持有有效令牌的调用方，能做的事情和在 Capture 的 Tcl 控制台里
直接打字完全一样——包括读写文件、启动进程，以及修改并保存原理图。

桥不检查、不改写、不批准提交的 Tcl。它把脚本当作不透明字符串转发。

## 实际的安全控制

| 控制 | 作用 |
| --- | --- |
| 只绑定 `127.0.0.1` | 局域网和公网无法访问，绝不要改成 `0.0.0.0` |
| 每次启动生成新的高熵 Bearer 令牌 | 上一次会话的令牌立即失效 |
| 所有接口都要求令牌 | 健康检查和内部轮询接口也不例外 |
| 描述文件放在当前用户的临时目录 | 其他 Windows 用户读不到 |
| 校验服务名、协议版本、Capture PID | 陈旧或不相干的描述文件会被拒绝 |
| 串行执行，一次一条命令 | 避免并发脚本互相干扰 Capture 状态 |
| 请求和响应有明确上限 | 限制内存占用 |
| 只能显式 `CaptureAiBridgeStart` | 加载脚本不会顺带打开通道 |

## 这些控制**防不住**什么

- **同一个 Windows 用户下已经在运行的恶意进程。** 它能读 `%TEMP%` 里的描述文件
  拿到令牌，也能直接检查 Capture 进程。本机令牌只能阻止无意的本地调用
  （比如某个网页或不相干的服务），不能阻止已经拿到同等权限的攻击者。
- **提交脚本自身的破坏力。** 由于桥有意执行不受限的 Tcl，一个脚本完全可以
  干扰桥的内部状态、Capture 本身，或者修改并保存设计。
- **长时间阻塞。** Capture 在它的 Tcl/UI 线程上执行脚本，死循环会让界面失去响应，
  而 HTTP 超时和客户端断开都无法终止它。

## 使用建议

- 不要在不可信的机器或多人共用的账户下启用本桥。
- 不要把令牌抄进聊天记录、日志、issue 或提交里；它每次启动都会变，没有共享的必要。
- 真正会修改设计的脚本，先在测试原理图上验证；桥不会自动保存，
  但脚本自己可以调用保存。
- 用完就 `CaptureAiBridgeStop`。退出 Capture 时父进程监视器也会让服务退出，
  但显式停止更可控。

## 日志

服务端记录生命周期和协议失败，但**不记录**令牌，也不记录提交的完整脚本。
Tcl 端把启动、停止、连接和协议失败报告到 Capture 控制台，消息经过脱敏，不含令牌。

`CaptureAiBridgeDumpPendingResult` 只在用户显式调用时才把待回传结果写到磁盘，
文件内容不含 Bearer 令牌。它是取证工具，不是自动日志。
